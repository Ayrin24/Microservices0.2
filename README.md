## Задача 1: Обеспечить разработку

### Выбор: GitLab (SaaS, gitlab.com) + GitLab CI/CD + GitLab Runner

Один продукт закрывает хранение кода (Git), сборку и доставку. Код и пайплайны живут в одном месте, поэтому не нужно связывать несколько систем вебхуками и токенами.

1. Для каждого микросервиса создаётся отдельный репозиторий, в корне лежит `.gitlab-ci.yml`.
2. Push или merge request автоматически запускает пайплайн.
3. Пайплайн разбит на стадии (`build` → `test` → `package` → `deploy`), задания исполняют раннеры.
4. Образ собранного сервиса публикуется в Container Registry, откуда его забирает деплой.

### Соответствие требованиям

| Требование | Как закрывается в GitLab CI |
|---|---|
| Облачная система | GitLab SaaS (gitlab.com), ничего не нужно разворачивать самим |
| Система контроля версий Git | GitLab — это Git-хостинг |
| Репозиторий на каждый сервис | Отдельный проект на каждый сервис, проекты объединяются в группу |
| Запуск сборки по событию из VCS | Пайплайн стартует по push, merge request, тегу; условия задаются через `rules:` |
| Запуск сборки по кнопке с параметрами | «Run pipeline» в интерфейсе: можно указать ветку и переменные; также доступны `when: manual` и запуск через API/триггеры |
| Привязка настроек к каждой сборке | Переменные пайплайна (`variables:`), переменные уровня проекта, группы и конкретного запуска |
| Шаблоны для разных конфигураций | `include:` (в том числе из общего репозитория с шаблонами), `extends:`, YAML-якоря, `.hidden`-задания как шаблоны |
| Безопасное хранение секретов | CI/CD Variables с флагами *masked* и *protected*, интеграция с HashiCorp Vault |
| Несколько конфигураций из одного репозитория | Несколько заданий и стадий, `parallel: matrix`, `rules:` по веткам/переменным, `include:` разных файлов |
| Кастомные шаги при сборке | В заданиях произвольные `script:`, `before_script:`, `after_script:` |
| Собственные docker-образы для сборки | `image:` в задании — можно использовать образы из своего Container Registry |
| Агенты сборки на собственных серверах | Self-hosted GitLab Runner (docker / shell / kubernetes executor) регистрируется в проекте или группе |
| Параллельный запуск нескольких сборок | Несколько раннеров и параметр `concurrent` в конфигурации раннера |
| Параллельный запуск тестов | Задания одной стадии выполняются одновременно, ключевое слово `parallel:` разбивает тесты на части |

### Обоснование

- Нужны Git, облако, шаблоны, секреты, собственные агенты и параллельность — всё это есть в GitLab из коробки, без плагинов.
- Конфигурация хранится как код (`.gitlab-ci.yml`) рядом с исходниками сервиса и версионируется вместе с ним.
- Общие шаблоны выносятся в отдельный репозиторий и подключаются через `include:`, поэтому для десятков микросервисов не нужно копировать один и тот же пайплайн.
- Чувствительная нагрузка (сборки с доступом к внутренней сети) выполняется на собственных раннерах, остальное — на облачных.

**Рассмотренные альтернативы**

- *Jenkins* — гибкий, но нужно самим обслуживать сервер и набор плагинов, а облачного варианта «из коробки» нет.
- *TeamCity Cloud* — подходит по требованиям (шаблоны, агенты, параллелизм), но Git-хостинг нужен отдельный, что добавляет ещё одну систему.
- *GitHub Actions* — тоже подходит, но шаблонизация и управление параметрами ручного запуска у GitLab CI удобнее для большого числа сервисов.

## Задача 2: Логи

### Выбор: Vector + VictoriaLogs + Grafana

1. Сервисы пишут логи только в stdout/stderr, никакой дополнительной настройки в приложениях не нужно.
2. На каждом хосте работает агент Vector. Источник `docker_logs` (или `kubernetes_logs` в кластере) читает логи всех контейнеров, добавляет метаданные (имя контейнера, образ, хост) и разбирает формат.
3. Vector отправляет события в VictoriaLogs. Если хранилище недоступно, события копятся в дисковом буфере и отправляются повторно после восстановления.
4. Разработчики ищут и фильтруют логи в Grafana через плагин VictoriaLogs (язык запросов LogsQL); у самого VictoriaLogs есть и встроенный веб-интерфейс.

### Соответствие требованиям

| Требование | Как закрывается |
|---|---|
| Сбор логов в центральное хранилище со всех хостов | Vector-агент на каждом хосте, единое хранилище VictoriaLogs |
| Минимальные требования к приложениям, сбор из stdout | Источник `docker_logs` / `kubernetes_logs` читает stdout контейнеров, приложение ничего не знает о системе логирования |
| Гарантированная доставка | Сквозные подтверждения (`acknowledgements`) и дисковый буфер (`buffer.type = "disk"`) в Vector: событие не теряется при недоступности хранилища или перезапуске агента |
| Поиск и фильтрация по записям | LogsQL: полнотекстовый поиск, фильтры по полям, потокам и времени |
| UI с доступом для разработчиков | Grafana (Explore и панели Logs) и встроенный веб-интерфейс VictoriaLogs; доступ разграничивается правами Grafana на папки и дашборды, а в самом VictoriaLogs доступна мультиарендность (tenants) |
| Ссылка на сохранённый поиск | В Grafana Explore запрос можно расшарить короткой ссылкой, а постоянные поиски оформляются как дашборд с панелью Logs и переменными (сервис, уровень, хост) |

### Обоснование

- VictoriaLogs сильно экономнее Elasticsearch по CPU, RAM и диску: хорошо сжимает данные и не требует тонкой настройки индексов и шардов, поэтому для команды микросервисов его проще эксплуатировать.
- Работает с тем же Vector, а значит гарантии доставки и формат сбора остаются прежними.
- Grafana даёт единый интерфейс: логи и метрики (задача 3) смотрятся в одном месте и могут быть на одном дашборде.
- LogsQL проще Lucene/KQL для типовых задач разработчика (найти ошибки сервиса за период).

**Рассмотренные альтернативы**

- *Elasticsearch + Kibana* — самый зрелый стек с богатым поиском и аналитикой, но тяжёлый по ресурсам и сложнее в эксплуатации. Хороший выбор, если нужна глубокая аналитика по логам или уже есть опыт с ELK.
- *Loki + Promtail + Grafana* — тоже лёгкий и привычный в Grafana, но индексирует только метки, а полнотекстовый поиск по содержимому заметно медленнее.
- *Graylog* — ещё одна платформа поверх Elasticsearch/OpenSearch, усложняет схему без явной выгоды.

## Задача 3: Мониторинг

### Выбор: VictoriaMetrics + vmagent + node_exporter + cAdvisor + Grafana (+ vmalert и Alertmanager)

1. `vmagent` опрашивает цели (pull-модель, тот же формат конфигурации, что у Prometheus) и отправляет данные в VictoriaMetrics.
2. На каждом хосте работают `node_exporter` (метрики железа и ОС) и `cAdvisor` (метрики контейнеров).
3. Сами сервисы отдают собственные метрики на `/metrics` в формате Prometheus, используя клиентские библиотеки.
4. Grafana подключается к VictoriaMetrics как к источнику данных и строит запросы на языке MetricsQL (расширение PromQL).
5. `vmalert` вычисляет правила алертинга и передаёт срабатывания в Alertmanager, который рассылает уведомления.

### Соответствие требованиям

| Требование | Как закрывается |
|---|---|
| Метрики со всех хостов | `node_exporter` на каждом хосте, `vmagent` собирает данные со всех экспортеров |
| Ресурсы хоста: CPU, RAM, HDD, Network | `node_exporter`: `node_cpu_seconds_total`, `node_memory_*`, `node_filesystem_*`, `node_disk_*`, `node_network_*` |
| Ресурсы каждого сервиса: CPU, RAM, HDD, Network | `cAdvisor`: метрики по каждому контейнеру (`container_cpu_usage_seconds_total`, `container_memory_usage_bytes`, `container_fs_*`, `container_network_*`) |
| Метрики, специфичные для сервиса | Эндпоинт `/metrics` в сервисе (клиентские библиотеки Prometheus): количество запросов, ошибки, задержки, бизнес-метрики |
| UI с запросами и агрегацией | Встроенный интерфейс VictoriaMetrics (vmui) и Grafana Explore: MetricsQL/PromQL (`sum by`, `rate`, `histogram_quantile` и т. д.) |
| UI с настраиваемыми панелями | Grafana: дашборды, панели, переменные, готовые дашборды для node_exporter и cAdvisor |

### Обоснование

- Экосистема экспортеров и клиентских библиотек Prometheus — де-факто стандарт, VictoriaMetrics полностью с ней совместима: собирает те же метрики, понимает PromQL и работает с готовыми дашбордами Grafana.
- VictoriaMetrics потребляет заметно меньше памяти и диска, чем Prometheus, и рассчитан на долговременное хранение: не нужно отдельно подключать Thanos или Cortex, когда метрик станет много.
- Режим single-node ставится одним бинарником или контейнером и не требует сложной настройки, при росте нагрузки есть кластерная версия.
- Grafana остаётся единым интерфейсом и для метрик, и для логов из задачи 2.

**Рассмотренные альтернативы**

- *Prometheus + Grafana* — де-факто стандарт и самый простой старт, но хранилище локальное, хуже масштабируется и требует дополнительных компонентов для долгого хранения. Это полностью рабочий вариант, если нужны минимальные отличия от привычной схемы.
- *Zabbix* — подходит для классического мониторинга хостов, но хуже приспособлен к динамичным контейнерным окружениям и метрикам приложений.
- *InfluxDB + Telegraf + Grafana* — рабочая связка, но push-модель и отдельный язык запросов делают её менее привычной для экосистемы микросервисов.
